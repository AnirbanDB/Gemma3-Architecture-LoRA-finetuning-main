Gemma 3 270M, built from the tensor up

What this repo actually contains

gemma3-270b-from-scratch-lora-finetuning.ipynb · 76 cells  +  README.md

The whole project is one notebook. It runs top to bottom as a linear pipeline with two distinct training phases separated by a checkpoint on disk. The rail on the left follows that order exactly — the numbering is the execution order, not a convenience.

01

Corpus and tokenization

cells 2–6

The pre-training corpus is TinyStories — synthetic children's stories written with a deliberately tiny vocabulary. The tokenizer is not trained; it borrows GPT-2's off-the-shelf BPE via tiktoken, which fixes vocab_size = 50257 throughout the model.

Tokenization follows nanoGPT's prepare.py: map each story to token ids with encode_ordinary (special tokens ignored), then stream every split into a flat np.memmap.

# cell 6 — one contiguous token stream per split
arr = np.memmap(f'{split}.bin', dtype=np.uint16, mode='w+', shape=(arr_len,))
for batch_idx in range(1024):                    # shard writes to bound RAM
    batch = dset.shard(num_shards=1024, index=batch_idx, contiguous=True)
    arr[idx : idx+len(arr_batch)] = np.concatenate(batch['ids'])
arr.flush()
Why uint16 is safe here. The largest GPT-2 token id is 50256, which fits in 16 bits. That halves the file versus int32 and, because the array is memory-mapped, the OS pages in only the slices a batch actually touches — training never loads the corpus into RAM.
02

Batch sampling: no epochs, just random windows

cell 8 · get_batch(split)

There is no DataLoader in Phase A. Each step draws batch_size random offsets into the token stream and slices two windows: inputs x = data[i : i+block_size] and targets y = data[i+1 : i+1+block_size]. The one-position shift is the next-token objective — no separate label construction exists.

ix = torch.randint(len(data) - block_size, (batch_size,))
x = torch.stack([torch.from_numpy(data[i   : i+block_size  ].astype(np.int64)) for i in ix])
y = torch.stack([torch.from_numpy(data[i+1 : i+1+block_size].astype(np.int64)) for i in ix])
x, y = x.pin_memory().to(device, non_blocking=True), ...   # overlap H2D copy

The memmap is re-opened every call. That looks wasteful but is deliberate: a long-lived memmap accumulates resident pages and leaks memory over a 17 000-step run.

03

RMSNorm, with Gemma's zero-centred weight

cell 13 · class RMSNorm

Gemma normalizes by root-mean-square only — no mean subtraction, no bias by default. Two details make this implementation match HuggingFace's Gemma 3 rather than a generic RMSNorm:

  • The learned scale is initialized to zeros and applied as (1.0 + scale). A fresh layer is therefore the identity, and weight decay pulls toward identity, not toward zero output.
  • The reduction is forced to float32 regardless of the bf16 activation dtype, then cast back. Squaring bf16 activations loses precision fast; this keeps the variance estimate stable.
x_f    = x.float()
var    = x_f.pow(2).mean(dim=-1, keepdim=True)   # no mean subtraction
x_norm = x_f * torch.rsqrt(var + self.eps)
out    = x_norm * (1.0 + self.scale.float())     # zero-centred weight
return out.to(input_dtype)
04

Two rotary bases, precomputed once

cell 12 · compute_rope_params, apply_rope

Position is injected by rotating query and key vectors, not by adding an embedding. Gemma 3 runs two RoPE frequency schedules and picks per layer:

Scheduletheta baseUsed byEffect
rope_local10 000sliding layersfast-rotating, fine local phase resolution
rope_global1 000 000full-attention layersslow-rotating, stays unambiguous over 32k positions

Both cos/sin tables are built for the full context_length at construction and stashed as non-persistent buffers — they are derived constants, so they move with .to(device) but never enter the checkpoint.

inv_freq = 1.0 / (theta_base ** (torch.arange(0, head_dim, 2)/head_dim))
angles   = positions[:, None] * inv_freq[None, :]
angles   = torch.cat([angles, angles], dim=1)      # duplicate to full head_dim

# apply: rotate the two halves against each other
x1, x2   = x[..., :head_dim//2], x[..., head_dim//2:]
rotated  = torch.cat((-x2, x1), dim=-1)
x_rot    = (x * cos) + (rotated * sin)
Half-split, not pair-interleaved. This is the "rotate-half" convention: dimension i pairs with i + head_dim/2. It is mathematically equivalent to the interleaved form but only if the projection weights were trained under the same convention — one reason weights from this notebook are not drop-in compatible with a differently-conventioned checkpoint.
05

Grouped-query attention: 4 queries, 1 shared KV

cell 13 · class GroupedQueryAttention

With n_heads = 4 and n_kv_groups = 1, this configuration is really multi-query attention: all four query heads read a single key/value head. The KV projections are consequently 4× narrower than the query projection, which is what shrinks the KV cache at inference.

QK-norm and the pre-attention scalar

Two stabilizers that plain attention omits. qk_norm=True applies an RMSNorm across head_dim to queries and keys before RoPE, bounding the dot-product magnitude. And the scale factor is query_pre_attn_scalar ** -0.5 = 1/16, taken from config rather than derived from head_dim — for this config the two coincide (both 256), but the seam exists so the scale can be pinned independently.

06

Two masks, built fresh each forward

cell 13 · Gemma3Model._create_masks

Gemma 3 interleaves cheap local attention with occasional global attention. In this 18-layer config, layers 5, 11 and 17 are full_attention; the other fifteen are sliding_attention with a 512-token window — a 5:1 ratio.

attend (mask = False) masked as future masked as too-far-past 
ones        = torch.ones((seq_len, seq_len), dtype=torch.bool)
mask_global = torch.triu(ones, diagonal=1)                      # j > i
far_past    = torch.triu(ones, diagonal=self.cfg["sliding_window"]).T   # i − j ≥ W
mask_local  = mask_global | far_past
07

The gated feed-forward (GeGLU)

cell 13 · class FeedForward

Three bias-free linears, not two. fc1 and fc2 both expand 640 → 2048 from the same input; one is passed through tanh-approximated GELU and used as a gate multiplying the other; fc3 contracts 2048 → 640.

x_fc1 = self.fc1(x)                                   # gate branch
x_fc2 = self.fc2(x)                                   # value branch
x     = nn.functional.gelu(x_fc1, approximate="tanh") * x_fc2
return self.fc3(x)
The notebook's inline comment calls this "combining both by concat" — the code in fact multiplies element-wise. Multiplication is correct for GeGLU; concatenation would require fc3 to take 4096 inputs, and it takes 2048.
08

The transformer block: four norms per layer

cell 13 · class TransformerBlock

Most decoder blocks carry two norms. Gemma 3 carries four — each sublayer is wrapped by a norm on the way in and another on the way out, before the residual add. The post-norms keep the residual stream from drifting in magnitude across 18 layers.

09

Assembling Gemma3Model

cells 13, 15 · class Gemma3Model, GEMMA3_CONFIG_270M

The top-level module is thin: an embedding table, 18 blocks built directly from the layer_types list, a final norm, and an untied output head. The forward pass carries both mask pairs and both RoPE pairs down to every block, letting each block pick.

x = self.tok_emb(input_ids) * (self.cfg["emb_dim"] ** 0.5)   # √640 ≈ 25.3 scale-up
mask_global, mask_local = self._create_masks(seq_len, x.device)
for block in self.blocks:
    x = block(x, mask_global=..., mask_local=..., cos_global=..., cos_local=...)
x      = self.final_norm(x)
logits = self.out_head(x.to(self.cfg["dtype"]))
loss   = F.cross_entropy(logits.reshape(-1, V), targets.reshape(-1)) if targets is not None else None
return logits, loss
The embedding scale-up matters. Multiplying by √emb_dim is a Gemma-specific step. Embeddings are initialized small; without this the first RMSNorm would amplify near-noise, and dropping it changes early training dynamics noticeably.

Configuration, annotated

A consequence worth naming. With sliding_window = 512 and block_size = 128, no query is ever more than 127 positions from any key — far_past is all-zeros and the local mask equals the global one. The sliding-window machinery is correct and exercised, but during this pre-training run the fifteen "local" layers behave identically to full-attention layers. The two RoPE bases still differ, so the layers are not equivalent.

Pre-training loop

cells 17, 19, 20, 22

Hyper-parameterValue

SequentialLR stitches warmup and cosine decay at the warmup_steps milestone, and — importantly — scheduler.step() is called only inside the accumulation branch, so the schedule advances once per optimizer step rather than once per micro-batch.

with ctx:                                    # autocast bf16
    logits, loss = model(X, y)
    loss = loss / gradient_accumulation_steps
scaler.scale(loss).backward()

if ((epoch+1) % gradient_accumulation_steps == 0) or (epoch+1 == max_iters):
    torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=0.5)
    scaler.step(optimizer); scaler.update()
    optimizer.zero_grad(set_to_none=True)
    scheduler.step()                         # once per real update
Two config quirks in this cell. min_lr = 5e-4 is larger than learning_rate = 1e-4, so CosineAnnealingLR's eta_min floor sits above the peak and the cosine leg anneals upward rather than down. And GradScaler is constructed with enabled=(dtype == 'float16') — on a bf16 GPU it is a no-op passthrough, which is correct, since bf16 does not need loss scaling.

Three decoders for three purposes

cells 13, 64, 67

The notebook accumulates three generation functions with different sampling behaviour. Knowing which produced a given sample explains a lot about the outputs in the README.

FunctionDefinedStrategyUsed for
Gemma3Model.generatecell 13multinomial, temp 1.0, optional top-kpost-pretraining story samples
generate_text_simplecell 64pure argmax (greedy)per-epoch progress prints
generatecell 67top-k + temperature, temp 0 → greedy, eos stopfinal instruction evaluation

All three re-crop the context to the last context_size tokens and take logits[:, -1, :]. None implement a KV cache — every new token re-runs the full forward pass over the whole prefix, which is quadratic and why 256-token generations are slow. The two later functions also handle the model returning a (logits, loss) tuple.

The final evaluation calls generate(...) with default temperature=0.0 and no top_k — so the instruction-following samples in the README are greedy decodes. Greedy decoding from a weak model is exactly what produces the locked-in repetition loops seen there.
12

LoRA, written by hand

cells 35, 36, 41, 42 · LoRALinear, add_lora_to_gemma3

No peft. LoRALinear wraps a frozen nn.Linear and adds a rank-r detour: base(x) + (x @ A @ B) * (alpha/r). The injector then walks every block and swaps seven projections in place.

Where the adapters land

add_lora_to_gemma3 freezes every parameter, then wraps seven linears per block: W_query, W_key, W_value, out_proj, fc1, fc2, fc3. Across 18 blocks that is 126 wrapped projections and 252 new tensors. Embeddings, the output head, and all 72 RMSNorms are left frozen and untouched.

for block in model.blocks:
    attn, ff = block.att, block.ff
    attn.W_query = LoRALinear(attn.W_query, rank, alpha)   # … k, v, out_proj
    ff.fc1 = LoRALinear(ff.fc1, rank, alpha)               # … fc2, fc3

optimizer = torch.optim.AdamW(
    filter(lambda p: p.requires_grad, model.parameters()), lr=1e-4)

The filter on the optimizer is the second half of the guarantee: freezing stops gradient accumulation, and filtering stops AdamW from allocating momentum state for 270M frozen tensors.

Wrapping preserves attribute paths. Because LoRALinear keeps the original module at .linear, the pre-trained weights stay in the state dict under a deeper key (…W_query.linear.weight). The swap must therefore happen after load_state_dict — which is exactly the order in cells 34 → 41. Reversing it raises unexpected-key errors.

Alpaca-style instruction data

cells 44–51

1 100 instruction/input/output entries are fetched from the LLMs-from-scratch repo and rendered into the Alpaca prompt template. The ### Input: block is emitted only when the entry has one.

def format_input(entry):
    instruction_text = ("Below is an instruction that describes a task. "
        "Write a response that appropriately completes the request."
        f"\n\n### Instruction:\n{entry['instruction']}")
    input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""
    return instruction_text + input_text

# the response is appended only inside the Dataset, never in format_input
full_text = format_input(entry) + f"\n\n### Response:\n{entry['output']}"

Split is a plain positional slice, no shuffle: 85 % train, 10 % test, 5 % validation. InstructionDataset pre-tokenizes every full text in __init__, so the DataLoader hands the collate function raw Python id lists rather than tensors.

SSL verification is explicitly disabled in download_and_load_file (check_hostname=False, CERT_NONE) — a Kaggle-environment workaround. It is worth removing before running this anywhere else.
14

The collate function does the real work

cell 55 · custom_collate_fn

Padding, shifting and loss-masking all happen here, per batch. Three things occur in sequence for every item:

  1. Append one <|endoftext|> (id 50256), then right-pad to the batch's longest sequence plus one.
  2. Slice the shift: inputs = padded[:-1], targets = padded[1:].
  3. Find every pad id in targets and replace all but the first with −100.
mask    = targets == pad_token_id
indices = torch.nonzero(mask).squeeze()
if indices.numel() > 1:
    targets[indices[1:]] = ignore_index      # −100
if allowed_max_length is not None:
    inputs, targets = inputs[:allowed_max_length], targets[:allowed_max_length]

Keeping the first pad token as a real target is what teaches the model to emit an end-of-text marker; masking the rest keeps the loss from being dominated by padding. allowed_max_length is bound to 1024 via partial, and device is passed in so tensors are built directly on the GPU (which is why num_workers = 0 — CUDA tensors do not survive worker processes).

The −100 does not currently take effect. Phase B computes loss in calc_loss_batch with a bare F.cross_entropy(logits.flatten(0,1), target_batch.flatten()) — no ignore_index=-100. PyTorch's default ignore_index is −100, so the masked positions are skipped by luck of the default; the mask works, but only because the default happens to match. Phase A's in-model loss has the same shape and no ignore handling at all, which is harmless there since raw corpus batches contain no padding.

Fine-tuning loop

cells 66–70 · train_model_simple

Phase B abandons the Phase A loop entirely for a conventional epoch-based one: iterate the DataLoader, zero_grad → backward → step, no accumulation, no scheduler, no scaler, no clipping. Every 5 steps it evaluates on 5 batches from each loader; after each epoch it greedily generates from a fixed validation prompt so drift is visible in the log.

SettingValue
epochs10
batch size8
learning rate5e-5
weight decay0.1
eval_freq / eval_iter5 / 5
model dtypebfloat16 (cast at cell 69)
The optimizer is rebuilt without the filter. Cell 42 constructs a correctly filtered AdamW, but cell 70 overwrites it with AdamW(model.parameters(), lr=0.00005, …). Because add_lora_to_gemma3 already set requires_grad=False on the base weights, no frozen tensor receives a gradient and none is updated — the LoRA contract holds. The cost is optimizer state allocated for every frozen parameter. Restoring the filter(lambda p: p.requires_grad, …) from cell 42 removes that overhead.

Results, and why they look like that

cells 30, 31, 74 · README

After pre-training

prompt Once upon a time there was a pumpkin. output Once upon a time there was a pumpkin. It was who wanted to see his heart also sad. Todd right bubbles with a Anna and juicy! Once upon a time there was a sail. The house and's dance dog…

Locally grammatical, globally incoherent — the model has learned TinyStories' register, cadence and vocabulary but not long-range structure. That is the expected shape of a 270M model trained for 17 000 steps at a 128-token context.

After LoRA fine-tuning

instruction Rewrite the sentence using a simile. input The car is very fast. response The moral of the word, the little girl is ' is ' is ' is 'I'm sorry.

The output collapses into a loop and reaches for storybook phrasing ("The moral of…"). Four causes compound, each visible in the code above:

Domain mismatch

The base model saw only children's stories. Nothing in TinyStories resembles ### Instruction:, so the adapter must teach an entirely new register — not adapt a familiar one.

Data volume

935 training examples over 10 epochs. Instruction-following typically needs tens of thousands; the adapter memorizes surface tokens instead of the task.

Adapter capacity

Rank 8 over 126 projections is roughly 1M trainable parameters against 270M frozen. LoRA steers a competent model; it cannot install a capability the base lacks.

Greedy decoding

Cell 74 calls generate at temperature=0.0 with no top_k. Argmax on a low-confidence distribution locks into the highest-probability cycle, which is the repetition you see.

What to change first

  1. Fix min_lr. Set eta_min below learning_rate so the cosine leg actually decays.
  2. Mask the prompt in the loss. Currently the model is trained to reproduce the instruction text as well as the response; masking everything before ### Response: concentrates gradient on the part that matters.
  3. Sample, don't argmax. Evaluating at temperature≈0.7 with top_k=40 would give a far more honest read on what the adapter learned.
  4. Raise the context. block_size = 128 against a 512 window means the sliding-attention path is never exercised; 512+ would make the architecture's local/global split real.
  5. Pre-train on prose before instruction-tuning. Or start LoRA from a base that has already seen non-story text.
